# 故事化技术讲解（Story-Taught Tech）

## Overview

把抽象的技术系统或概念映射成一个生活化的"类比世界"，用叙事让人**悟到**，而不是用定义让人**记住**。

本技能内置两种叙事模式，覆盖两种讲解粒度：

| 模式 | 适用对象 | 叙事策略 | 代表场景 |
|------|---------|---------|---------|
| **系统链路模式**（导览式） | 一个系统 / 一条完整链路 / 多个知识点 | 主角贯穿 + 术语即时标注 | 操作系统启动、JVM 类加载、TCP/IP 一次请求、数据库内核 |
| **单概念揭晓模式**（悬念式） | 一个孤立概念 / 术语 / 一句话定义 | 全程藏学名，结尾恍然大悟 | 死锁、CAP 定理、依赖注入、拜占庭将军 |

两模式共享同一套"承重墙 + 质量闸门"，只在叙事策略上分叉。

## 第 0 步：判定模式（每次必做）

- 要讲的是**一个系统、一条链路、或一组有先后/因果关系的知识点** → 系统链路模式（模式 A）
- 要讲的是**单个概念、术语**，或用户说"讲个寓言 / 打个比方 / 通俗理解 XXX" → 单概念揭晓模式（模式 B）
- 拿不准，或对象横跨两者 → 先问一句："你是想搞懂某个具体概念，还是想把整条链路从头到尾串一遍？"

## 共享层：两块地基 + 共用硬约束（两模式都强制）

### 地基一：先画"承重墙"，再动笔
动笔前必须先把技术本体拆清楚：
- 系统链路模式 → 列出 **5~10 个必讲知识点**（机制、流程、角色）
- 单概念揭晓模式 → 写出概念的**因果链**（什么触发什么、按什么顺序、导致什么结果）

**承重墙 = 漏一个就算失败。** 后续所有情节都要为这些点服务。

### 地基二：隐喻映射验证（写作前必做）
1. 列出 3~5 个计划使用的隐喻点，逐一标明映射到承重墙的哪一环
2. **覆盖检查**：承重墙的每一环都必须有对应隐喻；缺环 → 换结构，不要硬写
3. **机制 vs 主题检查**：映射的是"因→果→困境"的实际机制，还是只蹭了结果的主题标签？只蹭主题 → 重选
4. 全部通过才动笔

### 共用硬约束
- **奶奶测试**：隐喻载体必须是日常生活能直接感知的事物（做饭、排队、取快递、修水管、超市结账、解开缠住的耳机线……）。若载体本身需要解码（魔法符文、修仙体系、量子纠缠）→ 换掉。隐喻比概念更难懂，就违背初衷。
- **术语保留英文原词**（MMIO、DMA、BAR、IDT、GC、CAP）；故事语言在前，术语在后。
- **默认简体中文**；称呼用户可用"太子"。
- **图从简**：默认只用文字 + ASCII 简图（≤10 行）；别动不动就画 HTML 大图，仅当用户主动要图或文字确实讲不清时才出图。
- **反模式黑名单**（写作时主动避让，完整表见 references/method-details.md）：
  - 角色傀儡化｜隐喻过度｜揭晓过早｜故事空洞｜⚠️概念曲解｜⚠️隐喻比概念更抽象｜全程抽象无具体主角

## 模式 A：系统链路模式（导览式）

**A1 拆解必讲清单**：列出 5~10 个必须讲到的知识点（机制、流程、角色）——故事的承重墙。

**A2 选类比世界**：三个标准——① 结构同构（角色关系/流程方向/约束能一一对应，而非只像某一点）；② 用户熟悉（优先日常，不选另一个需要解释的领域）；③ 可扩展（能装下全部知识点）。
常用类比世界库：操作系统/硬件 → 小区物业、工厂车间、医院（前台/科室/手术室）；网络/TCP-IP → 快递物流、邮政系统、打电话；编译原理 → 翻译公司（口译=解释、笔译=编译）、后厨按菜谱做菜；数据库 → 图书馆（索引=目录卡、B+树=多楼层导引、事务=借还登记）；分布式 → 连锁餐饮（分店=节点、总部=协调者、外卖平台=消息队列）；JVM → 物业公司管写字楼（类加载=租户入驻、GC=保洁回收）。
拿不准就给 2 个候选类比并说明各自能覆盖哪些知识点，让用户挑。

**A3 构建角色对照表（先于正文）**：列"故事角色 ↔ 技术本体"对照表，每条注明**为什么对应**（功能相似点）。检查：每个知识点都有角色或情节承载、没有角色一人分饰两角、不冲突。对照表要进最终产出。

**A4 多幕叙事**（3~5 幕，每幕一个小标题）：
- 第一幕先立世界观，交代类比世界的基本设定，让用户"住进"故事里
- **跟着一个具体主角走**：用一条 mov 指令 / 一个快递 / 一次点餐贯穿全程，不要抽象概括（范例：`socket.send()` 的一生 = 寄一箱荔枝）
- 每幕埋知识点：术语在对应情节用括号或粗体自然带出（如"填工单（系统调用）"）
- 因果闭合：每个"为什么会这样"都要给机制层解释——类比负责"是什么感觉"，机制负责"为什么是这样"
- 结尾收束：一张极简 ASCII 图 + 一句话点破"类比世界的 X 就是技术里的 Y"

**A5 知识点零丢失校验**：逐条核对 A1 清单在哪个情节讲到，漏掉的补一幕或在收束段补齐；并自查有无"为了故事性牺牲准确性"的硬伤（类比可简化，但不能讲错）。

## 模式 B：单概念揭晓模式（悬念式）

核心理念：**先悟后知**——故事 → 沉浸 → 顿悟 → 揭晓。读者在不知道自己在"学什么"时已摸到本质，揭晓瞬间"原来讲的是这个"的情感锚定让记忆更牢。

**B1 理解概念**：提炼 2~3 个核心要素，写出因果链（见共享层地基一）。核心要素 = 必须映射的（≥2 个），隐喻点总量 3~5 个。

**B2 确认范围与场景（按需）**：概念多义/跨领域/表述模糊时，先确认理解（"我理解为 ______，核心要点是 ______，对吗？"）；概念离日常远时，简短问一句用户的工作或专业，以挑一个熟悉场景。日常场景已能精准映射时，不打扰用户。

**B3 选故事类型与语气**（详见 references/method-details.md）：
- 博弈/冲突 → 古代寓言；渐进累积 → 日常生活；系统涌现 → 自然/机械装置；"表面 vs 实际"反差 → 角色对话/说明书；工具/方案型（Node.js、缓存、依赖注入）→ 对比式（先"没有它"的困境，再"有它"的变化）
- 语气按概念情感色彩选：警示类→沉稳惋惜；反直觉类→轻快反转；两难类→中立；机制类→日常接地气

**B4 验证隐喻映射**（同共享层地基二）。

**B5 三段式写故事**：铺垫 60~70%（自然埋"神似"）→ 矛盾显现 20~30%（精准映射核心问题）→ 揭晓 10%（"这就是【概念名】"一句话点破，点到为止）。全程不出现学名，300~800 字，角色行为自然合理，隐喻点 3~5 个。工具/方案型必须展示"没有它"和"有它"两阶段。

**B6 附专业释义**：一句话定义 + 为什么重要 + 核心要点（是什么/为什么/怎么用）+ 故事元素|概念对应表 + 前置知识说明（引用生僻术语时补 1~2 句）+ 延伸思考 + （可选）续写钩子引出紧密关联概念（问题→方案、工具→常见坑、现象→相邻现象），只给一句话定义并问"需要展开讲吗？"。

**B7 自检**：7 条——角色自然度 / 隐喻准确性 / 故事独立性 / 揭晓时机 / 简洁度 / 具象化 / 术语闭环。**最多重写 2 次**，仍不过则输出当前最佳版并诚实告知用户哪里不够满意。

**B8 输出**：默认直接在对话中输出故事和释义，末尾问一句"讲清楚了吗？有不明白的地方、或者想换个场景讲，告诉我。"；用户要保存则写成 `概念寓言-{概念名}.md`。

## 输出结构（固定模板）

**系统链路模式**：① 开场一句（主题 + 类比世界 + 为何选它）→ ② 核心命题框（一句话说透本质）→ ③ 第 N 幕 ×3~5 → ④ 极简 ASCII 总结图（≤10 行）→ ⑤ **一句话总结（加粗，全文最有力的一句）** → ⑥ 角色对照表（故事角色 | 技术本体 | 对应理由）→ ⑦ 收尾一句指出类比边界（哪里像、哪里不像）。

**单概念揭晓模式**：① 寓言故事（不露学名）→ ② 揭晓句 → ③ 专业释义块（含故事-概念对应表）→ ④（可选）续写钩子 → ⑤ 一句"讲清楚了吗？"。

## 降级策略（概念/系统不适配时，别硬编）

1. 先尝试找到概念中**最具体的那个侧面**来讲
2. 找不到完整故事 → 改用"场景类比"（短比喻而非完整故事），如递归 = 站在两面对镜之间看到的无限层叠影像
3. 对象太宽泛（如"面向对象编程"）→ 建议用户缩小范围（"封装""多态"）
4. 找不到用户熟悉的合适场景 → 诚实告知并请用户换一个更日常的场景，不要硬凑别扭的强行类比

系统链路模式若无结构同构的日常类比世界 → 退回"分模块单概念揭晓"，逐个击破。

## 用户反馈处理（输出后触发，非工作流步骤）

- "隐喻不太准确" → 回到承重墙，重新确认核心矛盾/知识点理解，调整映射
- "故事不好/换一个" → 换故事类型与语气重写
- "太隐晦/太直白" → 调揭晓时机早晚，或增减铺垫篇幅
- "太长/太短" → 调铺垫部分的细节量，不改核心结构
- 多概念请求：有对比关系 → 可一个故事串两概念、结尾分别揭晓；无关联 → 分开讲；不确定 → 先问

## 质量红线

- 知识点 / 因果链丢失 = 失败（故事再好也没用）
- 类比讲错机制 = 失败（宁可少比喻，不可错比喻）
- 全程抽象概括、没有具体主角贯穿 = 平庸（重写成"某某的一生"式叙事）
- 对照表缺失 = 不完整（用户靠它把故事翻译回技术）
- 隐喻载体未过奶奶测试 = 不合格
